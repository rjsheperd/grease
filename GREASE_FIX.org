#+TITLE: Grease iOS nREPL — Fix Session Notes

* Goal

Get a live Clojure nREPL running on a physical iPhone (iPhone XR, iOS 16.6,
arm64e) via a GraalVM native-image binary (~bb.o~) linked into a SwiftUI app
(~MobileTest~). The UI should display:

1. Large title: ~CLOJURE BRIDGE~
2. Build-time hash of ~grease.clj~ (computed by Clojure/Graal)
3. Scrollable live log output
4. nREPL running / starting status

The nREPL is started from ~AppDelegate~ on a background GCD thread.

* What Does NOT Work / Open Problems

** 1. CAP Cache returns stale native code
~USE_CAP_CACHE=use~ (and even ~use~ after clearing the cache dir once then
rebuilding) served old compiled native code for ~clj_print_hi~. We saw
~(println "hi")~ output even after changing the function to ~(nlog "hi from
clj_print_hi")~.

*Fix applied*: Delete the capcache dir before each meaningful source change,
then rebuild from scratch.

#+begin_src bash
rm -rf /Volumes/MegaDisk2TB/Code/rjsheperd/clj-ios/grease/conf/capcache
# Then rebuild WITHOUT USE_CAP_CACHE=use
./ios-graal-jdk-21/scripts/build-bb-o
#+end_src

** 2. ~ffi/call "clj_log"~ does not reliably fire from Clojure

~clj_log~ IS exported from the MobileTest binary (~_clj_log T~ in ~nm~).
However, calling it via ~ffi/call "clj_log"~ from within bb.o appears to
either throw silently or do nothing.

*Current workaround*: ~nlog~ uses only ~println~ (which works from attached
threads and is captured by the stdout pipe redirect in Bridge.m).

#+begin_src clojure
(defn ^:private nlog [msg]
  (println (str "[Clojure] " msg)))
#+end_src

** 3. ~clj_start_server~ returns in ~56 µs (nREPL not started)

~clj_start_server~ is called with a properly-attached ~graal_isolatethread_t*~
but returns in ~50–60 µs — far too fast for nREPL initialisation. No
~[Clojure]~ log lines appear from inside ~clj_start_server~.

*Root cause (confirmed)*: CAP cache stale code. After clearing the cache and
doing a full clean build, this should be re-tested. The function itself is
correct.

** 4. New C entry points (~clj_get_hash_code~, ~clj_nrepl_port~) missing from bb.o

- The uberjar's ~com/phronemophobic/grease/interface.class~ has correct
  ~@CEntryPoint~ annotations for BOTH new functions (confirmed via ~javap~).
- ~build/bb/bb.h~ declares both functions (generated by native-image).
- ~nm build/bb/bb.o~ shows NO ~IsolateEnterStub~ for either function.

*Symptom*: Xcode linker fails:
#+begin_example
Undefined symbols for architecture arm64:
  "_clj_get_hash_code", referenced from: _call_hash_code in Bridge.o
  "_clj_nrepl_port",    referenced from: _call_nrepl_port in Bridge.o
#+end_example

*Likely cause*: Both new functions have signature ~() → long~ (no args besides
IsolateThread, return :int64). None of the original 8 working entry points
share this exact signature. This may be a bug in
~tech.v3.datatype.ffi.graalvm/expose-clojure-functions~ for zero-arg
long-returning functions.

*Suggested fixes to try (in order)*:

1. Change ~:rettype :int64~ to ~:rettype :int32~ and return an ~int~ — see if
   native-image generates stubs for that signature.

2. Add a dummy arg so the signature differs:
   #+begin_src clojure
   #'clj_get_hash_code {:rettype :int64 :argtypes [['unused :int64]]}
   #+end_src
   Call with ~clj_get_hash_code(thread, 0)~ from Bridge.m.

3. Bypass entry points entirely: use Bridge.m globals populated by parsing log
   output (grep for ~[Clojure] Hash:~ and ~nREPL server ready~).

4. Use existing ~call_eval~ from Swift to query Clojure state:
   #+begin_src swift
   // make grease-hash-code public first
   let id = call_eval("@com.phronemophobic.grease/grease-hash-code")
   // then call_prn(id) to print it (still can't get string back easily)
   #+end_src

* Key GraalVM Threading Rules

- One isolate per process; created via ~graal_create_isolate~.
- Each OS thread that calls Clojure code needs its OWN ~graal_isolatethread_t*~.
- Main thread: the handle stored in the global ~thread~ var (created at first
  ~call_eval~) — reuse this for all main-thread calls.
- Background GCD threads: always call ~graal_attach_thread(isolate, &bg_thread)~
  at the start and ~graal_detach_thread(bg_thread)~ at the end.
- Passing the main thread's handle to a background thread → CRASH (code 2):
  ~Fatal error: Failed to enter the specified IsolateThread context. (code 2)~
- Passing ~NULL~ to an entry point when ~-H:-SpawnIsolates~ is set → same crash.
