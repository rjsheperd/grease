#+TITLE: Grease Android Port — Clojure nREPL on Android
#+AUTHOR: RJ Sheperd
#+DATE: 2026-04-20

* Context

Grease runs a live Clojure nREPL on iPhone by compiling Clojure → GraalVM
native-image → ~bb.o~ (iOS arm64 relocatable object) → linked into an Xcode
~.app~. This document plans the parallel port to Android, enabling:

#+BEGIN_SRC bash
adb forward tcp:23456 tcp:23456
clj -M:repl/android   # connects to nREPL on device
#+END_SRC

Key discovery: GraalVM's ~Platform.java~ already defines ~ANDROID_AARCH64~
(line 353 of ~graal/sdk/src/org.graalvm.nativeimage/src/org/graalvm/nativeimage/Platform.java~).
The port is entirely additive — no iOS files change.

* Architecture

The iOS pipeline maps to Android with four surgical substitutions:

| Stage | iOS | Android |
|-------+-----+---------|
| JDK static libs | ~ios-graal-jdk-21/~ (Xcode + iOS SDK) | ~openjdk-mobile/~ (NDK clang, ~--openjdk-target=aarch64-linux-android~) |
| native-image output | Relocatable ~bb.o~ (~-H:+ExitAfterRelocatableImageWrite~) | Shared library ~bb.so~ (drop that flag) |
| Platform flag | ~-Dsvm.platform=...IOS_AARCH64~ | ~-Dsvm.platform=...ANDROID_AARCH64~ |
| App packaging | Xcode project (~.app~) | Gradle Android project (~.apk~) |
| C bridge | ~Bridge.m~ (ObjC + GCD) | ~bridge.c~ (pure C + pthread) |
| nREPL connect | WiFi direct (~device-ip:23456~) | ~adb forward tcp:23456 tcp:23456~ |
| Main-thread dispatch | ~dispatch_async(_dispatch_main_q, ...)~ | ~Handler(Looper.getMainLooper()).post(Runnable)~ via JNI shim |

What does *not* change: nREPL server, SCI interpreter, ~clj-libffi~, dtype-next
FFI, ~deps.edn~ dependencies, all domain Clojure logic.

** Architecture: JNI vs ObjC dispatch

On iOS, ~objc_msgSend~ is a universal "send any message to any object"
dispatch. Android has no equivalent — each API requires an explicit JNI shim.

| Aspect | iOS (~grease.ios.objc~) | Android (~grease.android.core~) |
|--------+------------------------+---------------------------------|
| Runtime dispatch | Universal ~objc_msgSend~ | Explicit C shim per method |
| Dynamic class creation | ~objc_allocateClassPair~ + ~class_addMethod~ | Not feasible from native |
| Main-thread dispatch | ~dispatch_async(_dispatch_main_q, ...)~ | ~Handler(Looper.getMainLooper()).post(Runnable)~ via JNI |
| Callbacks | ObjC blocks via ~grease_make_void_block~ | ~clj-libffi~ closure → JNI ~View.OnClickListener~ |

The ~on-ui-thread~ macro in ~android/repl.clj~ mirrors ~on-main~ from
~ios/repl.clj~ exactly: same promise/deliver/deref pattern, replacing
~dispatch-main-async~ with ~run-on-ui-thread!~.

JNI note: ~JNIEnv*~ is thread-local. Cache ~JavaVM*~ at ~JNI_OnLoad~; every
native→Java call gets ~JNIEnv~ via ~GetEnv()~ or ~AttachCurrentThread()~. The
~clj_generic_callback~ in ~bridge.c~ already demonstrates the isolate
thread-attach pattern — the Android JNI side follows the same model.
